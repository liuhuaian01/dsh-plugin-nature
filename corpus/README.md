# 语料库

这个目录的存在理由只有一个：**防止同一个误判发生第二次。**

插件走过三轮弯路，每一次都是真实文本打脸：

| 样本 | 首次判定 | 真实情况 | 根因 |
| --- | --- | --- | --- |
| 手写网文 | 40 分 C 级「明显的 AI 腔」 | 用户 100% 手写 | 一句一段被当成问题；省略号切分 bug |
| 雪中悍刀行 | 多次误报 | 专业作家成名作 | 「立马」被列为港台用词；首尾呼应被当成拼接 |
| 虎嗅财经稿 | 32 分 B 级 | 虎嗅编辑撰写 | 财经稿的标准排版和零口语被当成缺陷 |

三次的共同点：**那个体裁当时没有基准样本。**

## 怎么用

```powershell
$node = "C:\Users\claud\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe"
& $node test/regression.mjs    # 语料库回归，改任何规则之前先跑这个
& $node test/smoke.mjs         # 规则引擎行为
& $node test/integration.mjs   # dsh 契约
```

`regression.mjs` 是**地板线**。它不测「功能对不对」，测「对真实语料的结论稳不稳」。改动规则、阈值、文体画像之后，只要它绿，就说明没有把已经判对的东西弄坏。

## 目录结构

```
corpus/
  manifest.json     # 样本清单：体裁、平台、题材、来源、期望区间、误判历史
  channels.json     # 核心采样渠道：想覆盖什么、为什么、当前覆盖状态
  samples/*.txt     # 正文
  reports/          # 月度取证产出的报告
```

`manifest.json` 里每条样本的 `expect` 就是断言：

- `maxScore` — 分数上限（正常文本不该超过）
- `minScore` — 分数下限（对照样本要能检出）
- `mustNotHit` — 绝不该命中的规则 id（写清是哪次误判）
- `mustHit` — 必须命中的规则 id

**加样本时要一并写 `history`**，说清楚这次是什么误判、为什么会发生。未来改规则的人（可能就是我）看这一行就知道为什么这条断言不能动。

## 三维采样

语料按三个维度组织，因为规则误判几乎都来自其中一个维度没被覆盖：

- **体裁**（`genre`）— 决定规则阈值。句长下限、段落容忍度、是否要求「人声」，全看它。
- **题材**（`topic`）— 决定词汇分布。玄幻多古语，科技多外来词，财经多数字。
- **平台**（`platform`）— 决定排版惯例。一句一段在起点是常态，在年报里是异常。

`channels.json` 锁定了 9 个核心渠道。当前覆盖：

| 渠道 | 体裁 | 状态 |
| --- | --- | --- |
| 起点中文网 | webnovel | ✅ 2 个样本 |
| 虎嗅 / 36氪 | business | ✅ 1 个样本 |
| 晋江文学城 | webnovel | ⬜ 待收集 |
| 澎湃 / 界面 | news | ⬜ 待收集 |
| 头部公众号（评论） | commentary | ⬜ 待收集 |
| B站知识区口播稿 | script | ⬜ 待收集 |
| 上市公司年报 | report | ⬜ 待收集 |
| 官方技术文档 | tech | ⬜ 待收集 |
| 政府公开文件 | report | ⬜ 待收集 |

**7 个体裁里有 5 个是空的。** 这就是为什么规则会在那些体裁上出问题——不是规则写错了，是没人告诉它那个体裁的惯例是什么。

## 采样的注意事项

**取整篇，不要取片段。** 段落结构、小标题、开篇结尾都是体裁特征的一部分。切一段出来，统计就失真了。

**叙述段落优先于对话。** 节奏问题主要出在叙述里；对话天然短，会掩盖真实分布。

**来源要标清楚。** `source` 字段写「用户手写」「公开出版作品」「某某平台编辑撰写」——判断误报时，这四个字的区别是决定性的。

**版权。** 这些样本只用于本地回归测试，不再分发。公开作品优先取已发布且允许引用的内容；能自己写或取得授权的，优先用自己的。

## 月度取证

`corpus/reports/` 由每月一次的计划任务写入。那个任务**只做收集和报告，不改规则**。

理由：改规则的判据是「这符合该文体的惯例吗」，而惯例来自人，不来自统计。让一个只会给自己打分的系统去改自己，只会越来越自信，不会越来越准。
